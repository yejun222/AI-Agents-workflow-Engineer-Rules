针对需求「$ARGUMENTS」按下列顺序执行。**每步评审门**：每步子代理完成后，把它的摘要原文转述给我、列出产物文件路径（含如何打开预览），**评审门仅当我输入明确放行词（「确认继续」/「继续」/「下一步」）时才通过**——其他输入（含未明确表态的消息）先澄清、不推进；放行时我可能附修改意见，先执行对应修改再继续。步骤内嵌的决断提示（如第 7 步「接受 / 继续修复 / 终止」）按该步骤提示词处理，不受放行词限制。

0. **归档与变更控制**：先把原始需求原文归档到 `docs/00-brief.md`（由主对话写入；**归档即冻结，后续变更以 `CR-xx` 追加在文件末尾，不覆盖原文**）。若我明确说不用归档，则第 1 步把需求描述直接作为 product-manager 的输入，并**要求 product-manager 把需求原文写入 `docs/10-prd.md` 的「原始需求快照」小节（不加工，等价 00-brief 归档）**；以下各步输入清单一律去掉 `docs/00-brief.md`，测试角色以「原始需求快照」小节替代。
1. `/prd` → `docs/10-prd.md`（评审门）
2. `/proto` → `docs/20-prototype.html`（评审门）
3. `/arch` → `docs/30-architecture.md`（评审门）
4. `/impl` → `src/` 改动 + `docs/40-changelog.md`（评审门）
5. `/review` → `docs/60-review.md`（评审门）：若 60 存在致命 / 严重问题，转 engineer 修复（输入 60 + 相关上游契约，更新 40-changelog）→ 重跑 `/review` → **自动最多 1 轮**（重跑后 60 的 `REV-xx` 问题项须逐条标注 `已闭环 / 未闭环`，与 51 同规则）；仍存在则暂停交我决断（「继续修复」不计入自动循环上限 /「**接受残留**」→ 在 60-review 对应 `REV-xx` 问题项标注「已接受（用户决断）」，该问题不再阻断后续流程、测试阶段不纳入 51 跟踪 /「终止」）。⚠ 状态机行 5 的「带残留接受」**只针对 51 缺陷**（测试发现并跟踪的残留），不适用于本步的 60 审查问题。
6. `/test`（评审门）：先 test-designer 产出 `docs/50-testcases.md`（禁读 src，**软约束**——我抽查 50 是否泄漏实现细节（类名 / 函数名 / 表名），泄漏则打回 test-designer 重写），再 test-executor 产出 `docs/51-defects.md`、`docs/52-qa-report.md`（事实 + 建议结论）、`tests/e2e/**`。
7. **缺陷闭环**：按 `docs/state-machine.md` 从上到下判定并执行（含行 0 的 F4 前提、行 5 的残留接受路径；**判定条件不在本命令重复定义**，引用者不得改变被引用表的判定条件）；结论字符串只使用状态机的唯一枚举，不自行发明。**修复循环内每次 engineer 改动（40-changelog 变更）后，按 `docs/artifacts.md` 失效传播矩阵判断是否需回跑 code-reviewer；如回跑，`docs/60-review.md` 的 `REV-xx` 问题项须逐条标注 `已闭环 / 未闭环`（与 51 同规则）。** 我选择「接受」时，按下述模板转达给 test-executor：「用户已接受。接受人：<姓名>；理由：<原话>；补丁计划：<后续修复承诺>。」
8. **交付**：输出交付总结 = 产物清单 + 最终结论（由主对话按状态机签署）+ **已接受残留清单**（`已接受（用户决断）` 的 REV-xx 审查项与 `已接受` 的 BUG-xx 缺陷，含接受人 / 理由）+ **回滚方式**一节（说明每个交付单元如何回退：先回退哪个提交 / 文件，再验证什么）。每个交付单元对应一次**人工提交**（默认由我执行 `git commit`；自动提交仅在我明确授权时进行）。

## 规则

- **每步评审门（默认开启，严格模式）**：每步完成后先给我看产物摘要与文件路径，**仅当我输入明确放行词（「确认继续」/「继续」/「下一步」）才通过并派下一步**，其他输入先澄清、不推进；我提修改意见时转达对应子代理重跑该步。若我说「跳过评审」「直接跑完」，则关闭评审门、一口气执行到底（该逃生口不受放行词限制）。**缺陷闭环在评审门开启时仍逐次暂停；我要求的额外重跑不计入自动循环上限——该上限只约束由缺陷状态自动触发的循环（「最多 1 轮」「最多 2 轮」同此规则）。**
- 任一步骤产出「待确认清单」或「契约冲突上报」时，**暂停并向我汇报**，不要自行裁决。
- 若我只要其中某一步，用对应的单步命令（`/prd` `/proto` `/arch` `/impl` `/review` `/test`），不要跑全链。
- 不要跳过任何步骤，也不要让子代理互相调用。
- 若某步返回的摘要标注为「部分完成」（子代理达到轮次上限），续跑该子代理或把残留项报给我，不得进入下一步。
- 写盘步骤必须核验产物已落盘：返回摘要称已完成但文件不存在时，改为**前台重新调度**该步骤，不要凭摘要进入下一步。
- 上游契约变更后，按 `docs/artifacts.md` 的失效传播矩阵重跑受影响下游，并让各产物头部加失效标记。
