# 业务错误码注册表

> 用途：规范 `ApiResult.code ≥ 1000` 业务异常码的分配与登记，防止冲突和随意编造。
> 使用规则：**新增业务错误码前必须先查本表取号并登记**（随 MR 提交，登记人按阶段归属，见文末「登记人」）；已分配号码禁止复用或改义。系统码 `0` 为成功码，`0–500` 段与 HTTP 状态码对齐，**唯一例外是 `429` 限流：HTTP 429 而响应体 `code=1001`**，见全量规范 6.4（段标签与 6.4 正文逐字一致，由护栏 T28 绑定）。
> **护栏扫描面**（`tools/check-config.py` T15）：核验「正文引用的号码是否已登记」的范围 = `docs/development-spec.md`、`docs/30-architecture.md`、`docs/51-defects.md`、`docs/52-qa-report.md`、`docs/60-review.md`。**缩小扫描面等于允许「换个文件引用就绕过登记」**；改动本行必须同步 T15 的 `_CODE_SCAN_FILES`（二者由断言绑死，改一处即 FAIL）。T15 提取时跳过日期（实测 `如 \`2026-09-17T…\`` 会让年份被当成号码）。

## 分配规则

- 错误码为 4 位数字：前 2 位模块码段 + 后 2 位具体错误
- 模块码段分配：`10xx` 通用业务、`11xx` 用户模块、`12xx` 权限模块、`13xx` 数据/表单模块、`14xx` 报表/导出模块、**`15xx` 抽奖模块**（2026-09-17 首次申请）；新模块按顺序往后申请（`16xx`、`17xx`…）
- 每个模块内具体错误码从 `01` 递增，占满 99 个后再申请新码段
- 溢出策略：4 位码段 `10xx`–`99xx` 用满后启用 5 位错误码（`100xx` 起）或复用已废弃码段，启用前须在本表登记说明

## 使用边界

- `1001`（系统繁忙）：业务层主动降级提示（限流、熔断、依赖服务不可用等可重试场景）；`500`（系统内部错误）为全局 ExceptionFilter 兜底，业务代码禁止手动使用
- `1002`（业务层补充校验）：FluentValidation 等业务校验失败；`400` 为框架级绑定/模型校验（模型绑定、DataAnnotations），分工见全量规范 6.4
- `429`（限流）：**HTTP 状态码为 `429`，响应体却是 `code=1001`** —— 全量规范 6.4 表中**唯一一处 HTTP 状态码与 `code` 取值不同**的组合（`0` 与 `0–500` 段其余取值两者一致）。前端一律按 `code` 判定（`1001` 的可重试降级路径），**不得按 HTTP `429` 另立分支**——否则同一条限流会有两套前端处理。语义由架构 §5.1 / §5.2 规定
- `1102`（用户名或密码错误）：登录失败**统一文案**，不得区分「用户不存在」与「密码错误」，防账号枚举（FR-02 / AC-04）
- `1103`（账号锁定）：连续 5 次登录失败触发；**对不存在的用户名同样计数**，否则锁定行为本身会成为账号枚举信道
- `1203` / `1204`：业务异常按规范 6.4 返回 **HTTP 200**，故刷新接口失败**不会**进入 axios 错误分支，前端刷新函数必须自行判断 `response.data.code`（规范 3.4）
- `1501`（次数用尽）：**后端为准**，绕过前端直调同样拦截（FR-04 / FR-07 / AC-10）
- `1502`（奖品抽完）：候选集为空的兜底；默认奖池含常驻「谢谢参与」，正常不触发（FR-05-R3）
- 密码强度校验失败走 `1002`（FluentValidation 业务校验），**不单列错误码**

## 登记流程

1. 查本表确认模块码段与已用号码
2. 取模块内下一个可用号码（递增）
3. 在本表追加一行，随代码 MR 一起提交
