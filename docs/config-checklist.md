# 配置交叉核对清单（config-checklist）

> **能机械断言的检查项已移入 `tools/check-config.py`**（`python3 tools/check-config.py` 一键运行）。本清单只保留**需要人判断**的条目：改动角色 / 命令 / 文档后，先跑脚本，再按下面逐条人工过一遍。

## A. 产物登记表回溯

- [ ] `docs/artifacts.md` 的「读取者」列，是否与每个角色文件「输入要求」里读的文件**逐一对上**（含新增角色、新增产物）？
- [ ] 产物路径变更时，`/feature`、单步命令、`docs/state-machine.md` 里引用的路径是否同步更新？

## B. 编排命令回溯

- [ ] `/feature` 每一步的输入清单，是否与 `artifacts.md` 的读取者列一致？
- [ ] 每个含条件的步骤（如"若我说不用归档"）是否列出了**全部**受影响的步骤？⚠️ 只排除"后续"步骤、漏掉该步骤自身的输入，是本清单反复放过的形态。
- [ ] 每个「暂停等我决定 / 交给我决断」是否都写了**我选 A 做什么、选 B 做什么**？只有暂停没有后续动作 = 悬空分支。
- [ ] 新结论/新分支（如"带残留接受"）是否同时在发布门槛/状态机里**定义了该结论**？只有一个文件提它 = 无定义结论。
- [ ] 计数器（"最多 2 轮 / 1 轮"）是否说明：人工触发的重跑算不算进上限？
- [ ] **本次是否引入或修改了「同一事实的第二个落点」**（精简版 ↔ 全量版、规范正文 ↔ 角色提示词、契约 ↔ 用例、同一配置的多个消费点、同一编号的多份产物）？是 → **必须同步新增一条把两处逐字绑定的护栏断言**（范式：`check-config.py` 的 T14 / T16），否则必然分叉。⚠️ 本仓库实测的**六个不同领域的坑是同一个根因**（客户端/服务端超时配置、前端/后端超时预算、同一事务多个写路径的错误分类、同一配置的三处兜底、产物编号撞车、规范正文引用未登记的号码）——不要因为"这次只是文字"而跳过

## C. 状态机与结论一致性（脚本已查字符串，人工查语义）

- [ ] `docs/state-machine.md` 每个结论分支，在 `/feature` 与测试角色里的**执行动作**是否自洽（谁能触发、谁落盘、谁签署）？
- [ ] 测试角色的「建议结论」范围是否**明确排除了**只有主对话能授权的结论（有条件发布（含残留缺陷））？
- [ ] 修复循环出口已定义：第 2 轮后只要存在未消除阻断项（不限致命 / 严重）就交用户决断（state-machine 修复循环 c「出口与缺陷级别解耦」）；修复分派按触发原因 —— **每一类阻断项都必须有 owner，否则行 4 会在 a 处原地停滞**：缺陷 → engineer；覆盖 / 用例缺口 → 测试角色；契约冲突 / 待确认清单 → 主对话裁决；阻断型 OBS → 按领域归属（环境 / 证据 / 工具链类由主对话调度）；上游「待复核」→ 按 artifacts §5 重跑；未闭环 REV → code-reviewer。
- [ ] **判定行前提与它声称拦截的事实是否匹配**（`state-machine.md`）：行序是「首个命中即结论」，**任何一行漏了某前提，它之前定义的那类事实就会被静默吸收**。逐行核对：行 0.5 / 1 / 2 / 3 / 3.5 是否都带「无其他阻断项（D2）」？（缺一处即让 D2 在该行失效——实测原表只有行 4 含该条件，覆盖达标时 D2 恒为死条件。）行 2 / 0.5 / 3.5 是否都带「覆盖达标 / 覆盖不达标」前提？**新增或修改判定行后，必须回到本项重核，并同步 T24 的逐行断言**（T24 是逐行匹配，不是计数）。
- [ ] **状态机的「表注 ↔ 历史节」分工未被打破**（T29 已机器断言）：`docs/state-machine.md` 判定顺序表下方的**表注**＝**尚未被改的现行约束**（行序要求：行 0.5 必在行 1 前、行 3.5 必在行 4 前、行 3.5 必带「无未闭环致命 / 严重」前提），文末**修订记录（历史，不回改）**＝**当时的事实**，按 13.4 不回改。**不要把表注里的约束移回历史节**：两者性质相反，混在一处会让改表的人分不清哪句还在生效——本次修订前整个块**零断言覆盖**，里面还长期存活着一条不成立的表述（「使 D2 项**一律**下落到行 4」，在 `F1 = 是` 时为假）。**行 5 是本表唯一的 D2 刻意例外**：它的前提里**不含**「无其他阻断项（D2）」——因为 `F1 = 是` 时行 0.5–4 全部不命中，且行 5 之后**没有兜底行**，给它补上该前提会让该场景**无任何行命中**。正确改法是保留例外、补**披露义务**（逐条登记 D2 四类 + 逐条列入交付总结的已接受残留清单），不是补前提。

- [ ] 已跑 `python3 tools/check-config.py`，全部断言通过。
- [ ] 本次新增 / 修改 `tools/check-config.py` 断言后，已运行 **`python tools/check-config.py --self-test`** 并全部通过？该命令把本项要求自动化：逐条突变 → 断言目标断言 FAIL → 还原 → 断言恢复全 PASS。⚠️ **每例必须先断言「变更确实发生」**——不先断言，`replace` 未匹配会静默不动，于是「没验证」被当成「验证通过」，把假阴性写进护栏。新增断言后**必须把对应突变追加进 `MUTATIONS`**，否则新断言永远没被负向验证过。
- [ ] 护栏自测本身也有辨别力：突变**必须破坏锚句在该文件中的全部落点**（用 `replace` 全量替换，不要 `count=1`）。实测教训：锚句在同一文件中**可能有多个落点**——只改第一处时锚句仍在同一文件的其他位置，自测报「未捕获」——那是**突变太弱**，不是护栏瞎了，别据此去删断言。
