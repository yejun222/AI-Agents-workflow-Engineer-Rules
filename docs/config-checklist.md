# 配置交叉核对清单（config-checklist）

> **能机械断言的检查项已移入 `tools/check-config.py`**（`python3 tools/check-config.py` 一键运行）。本清单只保留**需要人判断**的条目：改动角色 / 命令 / 文档后，先跑脚本，再按下面逐条人工过一遍。

## A. 产物登记表回溯

- [ ] `docs/artifacts.md` 的「读取者」列，是否与每个角色文件「输入要求」里读的文件**逐一对上**（含新增角色、新增产物）？
- [ ] 产物路径变更时，`/feature`、单步命令、`docs/state-machine.md` 里引用的路径是否同步更新？

## B. 编排命令回溯

- [ ] `/feature` 每一步的输入清单，是否与 `artifacts.md` 的读取者列一致？
- [ ] 每个含条件的步骤（如"若我说不用归档"）是否列出了**全部**受影响的步骤？⚠️ 只排除"后续"步骤、漏掉该步骤自身的输入，是本清单反复放过的形态。
- [ ] 每个「暂停等我决定 / 交给我决断」是否都写了**我选 A 做什么、选 B 做什么**？只有暂停没有后续动作 = 悬空分支。
- [ ] 新结论/新分支（如"带残留接受"）是否同时在发布门槛/状态机里**定义了该结论**？只有一个文件提它 = 无定义结论。
- [ ] 计数器（"最多 2 轮 / 1 轮"）是否说明：人工触发的重跑算不算进上限？

## C. 状态机与结论一致性（脚本已查字符串，人工查语义）

- [ ] `docs/state-machine.md` 每个结论分支，在 `/feature` 与测试角色里的**执行动作**是否自洽（谁能触发、谁落盘、谁签署）？
- [ ] 测试角色的「建议结论」范围是否**明确排除了**只有主对话能授权的结论（有条件发布（含残留缺陷））？
- [ ] 修复循环出口已定义：第 2 轮后只要存在未消除阻断项（不限致命 / 严重）就交用户决断（state-machine 修复循环 c「出口与缺陷级别解耦」）；修复分派按触发原因（缺陷 → engineer，覆盖 / 用例缺口 → 测试角色）。

## D. 交付前核查

- [ ] 角色文件：frontmatter 完整（`name` / `description` 双引号 / `tools` / `model` / `maxTurns` / `color`），description 含"不负责 → 其他角色"互斥指向。
- [ ] 写入范围：每个角色「可写 / 只读」与 `artifacts.md` 速查表一致；`Bash` 用途已限定（构建 / 测试 / 验证）。
- [ ] 已跑 `python3 tools/check-config.py`，全部断言通过。
- [ ] 本次新增 / 修改 `tools/check-config.py` 断言后，是否**逐条负向验证**（故意破坏 → 断言必须 FAIL → 还原 → 必须 PASS）？⚠️ **每例必须先断言「变更确实发生」**——不先断言，`replace` 未匹配会静默不动，于是「没验证」被当成「验证通过」，把假阴性写进护栏。
- [ ] 反向核对：把「暂停」点全部列出来（`/feature` 第 0/5/7 步 + 各角色待确认清单 / 契约冲突上报），逐个确认有后续动作。
- [ ] 结论字符串比对：`state-machine.md` ↔ `test-executor` 逐字一致，test-executor 不得自造状态机未定义的结论；`/feature` 只允许引用状态机（形式：按 `docs/state-machine.md` 判定），**不得出现裸结论字符串**；每个结论分支必须可达（有一个分支永远走不到，就是死分支）。
- [ ] `60-review` 的 REV 编号与状态（`未闭环` / `已闭环` / `已接受（用户决断）`）已在 `docs/artifacts.md` ID 体系登记；`已接受（用户决断）` 仅在主对话转达后由 code-reviewer 落盘。
- [ ] 无同名 agent 文件（同名只加载一个，且 `/doctor` 会报警）；新角色已进 `README.md` 角色清单与交接链图。
- [ ] `role-protocol.md` §5（启动 / 就绪）与 `tests/e2e/**` 实际代码是否一致：启动 helper **唯一**、`cwd` 锁死发布目录、就绪判据走**依赖配置最深**的那条路径（`/health`、匿名接口、`401` 类判据都是**伪就绪检查**）。⚠️ 实测出现过**规则已改而门禁判据未改**的情形（规则写「必须签发令牌」，脚本的就绪门禁仍是 `GET /prizes → 401`，签发调用排在门禁**之后**）——两者不一致时以**脚本实际行为**为准排查，不得拿规则文本当作已生效的证据。

## E. 已知优化（未启用，改动前先读这里）

- [ ] **环境约束单点登记（未启用）**：跨产物反复复述的环境约束（如「路径含 `&` → `npm run *` 不可用」「控制台 GBK」）**暂不引入 `env-constraints` 单点文件**——当前仅 2 条，且各自已有天然落点（命令表 / `role-protocol` §6）；为 2 条事实建编号体系的登记成本高于收益。**触发条件**：累积到 **4–5 条**，或出现「同一约束在不同产物里给出**互相矛盾**的处置」时，升级为单点登记（届时须同步 `artifacts.md` 的 ID 体系、`check-config.py` 三向对齐与本节）。**已签署产物中的历史复述不回改**——属"当时如实记录"，回改会破坏取证价值。
- [ ] **test-designer 与 engineer 并行（v2 候选）**：依赖分析成立——test-designer 输入 10/20/30，不消费 40，第 4 步起可与 engineer 并行，`/feature` 关键路径 7 段 → 6 段。未启用原因：并行派发 + 合并评审门复杂化编排，收益仅一次评审暂停；缺陷闭环期间 engineer 反复回跑不受益。启用前重新评估，并同步 50-testcases 输入语义与评审门放行词规则。
