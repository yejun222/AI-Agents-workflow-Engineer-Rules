# 角色公共协议（所有角色必须先读）

本文件 + `docs/artifacts.md` 与各角色文件共同构成行为约定。**角色文件的「输入要求」应声明先读本文件；冲突时角色文件本身说了算**（它就是该子代理的系统提示）。公共章节只在此定义一份，各角色文件不再重复。

## 1. 总则

- **产物交接的唯一通道是 `docs/artifacts.md` 登记的文件路径**。子代理不继承主对话历史，产物内容靠文件传递，不靠返回摘要（摘要有损压缩）。返回摘要只报告位置与要点，不重复产物全文。
- **写盘必须核验落盘**：返回摘要称已完成但文件不存在时，视为未完成并如实上报。
- **上游契约只读**：`docs/artifacts.md` 标为只读的文件一律不得修改；只写自己「写入范围」列出的文件。
- **禁止递归委派与互相调用**：本配置的 `tools` 白名单不含 `Agent` / `Task`；不产生子代理、不向其他角色派活。
- **上下文省读**：只读需要的段落。先用 Grep 定位关键词，再定点 Read 相关小节，不整份读契约。
- **版本与冻结**：契约文件（00/10/20/30/50/51/52/60）头部含元信息块（产物 / 版本 / 冻结时间 / 上游依赖）；冻结后变更须生成新版本。上游变更后，下游产物须在头部标注「上游 vX 变更，本产物基于 vY，待复核」（失效标记）。需求变更以 `CR-xx` 编号追加在 `docs/00-brief.md` 末尾，不覆盖原文。
- **不提交代码**：任何角色不得 `git commit` / `git push`，除非主对话在调度指令中明确要求。**主对话会在每个评审门后做 wip 提交**（`wip(step-N): …`，用于产物保护与取证）——你在 `git log` 中看到 wip 提交**属正常，不构成你可以自行提交的先例**。
- **能用 diff 就别用旁证（取证优先级）**：wip 提交意味着每一步的产物都有**版本控制级**凭据。凡需要证明「某文件被改过 / 未被改过」时，**首选** `git diff <基线SHA>..<wip 提交> -- <路径>` 或 `git show`；只有当目标确实不在版本控制下时，才退而使用「改动痕迹检索 + mtime + 锚点互证」这类**旁证**，且**必须在产物中显式标注证据强度为「旁证」而非「版本控制级」**（不得含混表述）。
- **同一事实禁止多落点；不可避免时必须由护栏绑死**：同一个事实（数值、口径、路径、结论字符串）只允许在**一处**定义，其余处**引用 ID**；确需在两处出现时（如精简版与全量版规范各写一份），**必须同时新增一条把两处逐字绑定的护栏断言**，否则必然分叉——本仓库实测的这些坑是**同一个根因**：客户端超时 vs 服务端超时、前端 vs 后端超时预算、同一事务多个写入点的错误分类、同一配置的三处各自兜底、同一编号在两份产物中指向不同内容、规范正文引用了未登记的号码。成功范式见 `tools/check-config.py` 的 T14（`development-spec` ↔ `CLAUDE.md` 措辞逐字一致断言）——**新增双落点事实时照此办理**。

## 2. 信息不足时的处理（无法提问）

子代理在独立上下文中运行，**无法向用户直接提问**。因此：

1. 信息缺失时不要空转、不要反复重试、不要编造。
2. 基于现有信息产出**完整草案**，在草案末尾附「待确认清单」：

   | 编号 | 缺失信息 | 我采用的默认假设 | 若假设不成立的影响 |
   | --- | --- | --- | --- |
   
   **编号与落盘（护栏 T30 机检）**：待确认项一律用 `QX-nn`（`docs/artifacts.md` §3 唯一现行前缀；复合形态 `QX-<发起角色首字母>-nn` 同属该序列），**落盘在本产物内的「待确认清单」节**（体例：`docs/50-testcases.md` §6、`docs/40-changelog.md` §「待确认清单（默认假设）」）；跨产物引用必须带文件名前缀（`50:QX-02`）。**不得就地自造前缀**——本仓实测同一类事实被自造出 `AS` / `QA` / `CAR` 三个前缀，跨文件检索无法收敛；三者已补登记为「既有前缀，不再新造」。

3. 在返回摘要首行写明：「存在 N 项默认假设（Q1…Qn），需主对话确认后再定稿」。
4. 只在「缺失信息会导致产出物在结构上不成立」时才中断，并在摘要中写明「无法继续，缺 X」。其余情况一律产出草案 + 假设清单。

## 3. 返回摘要格式

产物写入约定路径后，返回 ≤ 200 字摘要，固定三段：

1. **产物**：文件路径 + 一句话说明
2. **关键决策**：最多 3 条（做了什么选择、放弃了什么）
3. **待处理**：`待确认清单` / `契约冲突上报` / `无`

不要在摘要里重复产物全文。

**判定基准声明（条件性，有并行改写时必写）**：若本次判定所依赖的上游产物在你工作期间**可能被并行修改**，须在第 1 段后附一句声明 —— 「本产物基于 `<文件>` v<N> 判定；`<文件>` 并行更新中，未依赖其新版本」。多 agent 并行时这是唯一能让「判定与上游不一致」被发现的机制；缺此声明，读者会默认你依据的是最新版本。

## 4. 冲突上报

发现上游契约冲突且无法按判定基准裁决时：在返回摘要中用「**契约冲突上报**」开头单列一段，写清各方各自怎么说（引用稳定 ID）、你的倾向、为什么不自行裁决。不要修改任何一份上游契约文件。

## 5. 启动后端实例的前置条件（E2E / 集成验证必读）

违反以下任一条都会得到**误导性的失败结果**（本仓库实测踩过，表象与真实原因完全不符，排查成本极高）：

1. **必须先进到发布目录再启动**：`dotnet <相对路径>.dll` 会把 **ContentRoot 设为当前工作目录**，导致 `appsettings*.json` 不被加载 → 签名密钥为空 → **所有接口返回 500，且日志文件 0 字节**（表象是"程序没起来"，真实原因是配置没读到）。
   - ✅ `cd <publish 目录> && dotnet <项目名>.dll`
   - ❌ 在仓库根目录 `dotnet tests/e2e/deploy/xxx/项目名.dll`
2. **启动逻辑收敛为唯一模板，不许各脚本各写一份**：`tests/e2e/**` 下只保留**一个**启动 helper，其余脚本一律调用它。逐份复制的启动代码正是第 1 条反复复发的原因——每份都可能漏掉 `cwd`。

   ```js
   // ✅ 唯一模板（Node / Playwright）：cwd 锁死发布目录；stdout/stderr 必须落文件，否则第 1 条故障只剩 0 字节日志
   const child = spawn('dotnet', [PUBLISH_DLL], {
     cwd: PUBLISH_DIR,                              // ← 关键行：工作目录 = 生产产物目录
     env: { ...process.env, ASPNETCORE_URLS: `http://localhost:${port}`, ...env },
     stdio: ['ignore', 'pipe', 'pipe']
   });
   ```

   本仓库既有实现：**`tests/e2e/lib/launch-api.mjs`**（唯一一份；`coverage.spec.ts` 已改为从它导入，自身不再保留任何启动实现）。分发到新项目时按本项目路径替换该文件内的 `PUBLISH_DIR` / `CONNECTION_STRING`。
   - **手工起实例也必须走它**，不要手敲 `dotnet <路径>.dll` —— 实测出问题的正是这条手工路径（`cwd` 由人的位置决定）：
     `node tests/e2e/lib/launch-api.mjs --port 5199 --log <用途> --env Draw__DailyLimit=30000`
     该入口自带**真实就绪检查**（走签发令牌路径），未通过即以非 0 退出并提示「后续一切用例失败结论无效」。
3. **必须用「签发令牌」做就绪检查，且判据走依赖配置最深的那条路径**：仅探测端口连通、`GET /health` 或**任何匿名可访问的接口**都**不足以**证明实例可用——配置缺失时进程照样监听端口、照常回状态码。
   - **签发路径按项目定**（注册或登录），必须是**用例实际会走的那条**：本仓库为 `POST /api/v1/auth/register`。只钉死一条示例路径，照抄者就会漏掉自己项目里真正会坏的那条。
   - **为什么 `401` 这类判据永远测不出配置缺失**：请求不带 token 时，认证中间件**根本不会进入签名校验**——签名密钥为空它照样返回 `401`。这不是"另一种可接受的探活方式"，是**伪就绪检查**：故障态与正常态给出**完全相同**的信号。（本仓库实测：原有前置核验判据为 `GET /prizes → 401`，恰好绕过唯一会坏的那条路径，烧掉整整 45 轮。）
   - 未通过此检查就开跑，得到的失败结论**无效**——后续每一条"用例失败"都可能只是环境未就绪的假象。
4. **就绪检查必须覆盖「测试工具链自身」，不只是后端实例**：本仓库实测，两种「环境没搭好」都以**产品缺陷的表象**出现——58 条用例里 55 条同时失败，看起来像产品大面积崩了。二者都躲过了常规探测：
   - **浏览器内核缺失**：Playwright 的浏览器**不在 `npm ci` 范围内**（`node_modules` 装好 ≠ 浏览器可用）。缺了它，**所有需要浏览器的用例在 1ms 内瞬时失败**（报 `browserType.launch: Executable doesn't exist at ...`），而**纯 API 级用例照常通过**——于是"3 通过 / 55 失败"极易被读成"产品坏了"。一次性安装：`node node_modules/@playwright/test/cli.js install chromium`。
   - **前端 dev server 未真正可用**：`GET /` → **200**、`GET /api/...` → **401**、`GET /src/main.ts` → **200**，**三个探测全部"正常"**，但浏览器执行不了模块图 → **应用从未挂载** → 所有浏览器用例 30s 超时。**`GET /` 返回 200 不算前端就绪**（本仓库成因：仓库绝对路径含 `#`，见「一、常用命令」的环境前提）。
   - ✅ **唯一可靠的前端就绪判据：用浏览器实际断言应用已挂载**——等一个 `page-*--default` 锚点出现，而不是任何 HTTP 状态码。本仓库做法：dev server 起来后用 Playwright 打开 `/login`，等 `[data-testid="page-login--default"]` 出现才算就绪。
   - **失败归因纪律**：若失败用例的报错是 `browserType.launch` / `ECONNREFUSED <端口>` / 页面里找不到任何 `page-*` 锚点，**一律先判「环境未就绪」**，其失败结论**全部无效**，不得据此记缺陷。**先隔离复跑，再定性**——本仓库实测：全量跑超时的 4 条用例，隔离复跑 4/4 秒过（1.1–4.8s）。
   - **第二类签名：超时 + 共享配额（用例隔离缺陷，不是环境未就绪、也不是产品缺陷）**：失败报错为 `Test timeout … exceeded`（**非断言失败**）、用例以注册 / 登录开头、**全量串行时复现而 `--grep` 隔离复跑秒过** → 判「**用例隔离缺陷**」，按 `docs/development-spec.md` 7.6 登记为 OBS（含根因 + 处置计划），**不得据此记产品缺陷**。本仓库实测：两轮共 10 条次此类"失败"，根因全是共用出口 IP 的注册 / 登录限流窗口与共享库状态。**同一签名跨 ≥2 轮复发 → 必须补用例隔离手段，不得继续用「隔离复跑通过」放行。**

## 6. Bash 调用约定（Windows / Git Bash）

- **环境变量赋值时不要给变量名加引号**：`"VAR=value" cmd` 中 `"VAR=value"` 被 shell 解析为**命令名**而非赋值，会以 `exit 127: command not found` 失败（表象像"命令不存在"，实际是赋值没生效）。
  - ✅ `VAR=value cmd`（**推荐**；变量名不加引号，值含空格或特殊字符时只给**值**加引号：`VAR="a b" cmd`）
  - ⚠️ **不要用 `env VAR=value cmd`**：`env` 只是 PATH 上的一个普通命令，**可能被同名脚本劫持**。本仓库实测：`~/.local/bin/env` 被 **uv 的 PATH 片段**占据（那本该被 `source`，不该被执行），它**只改 PATH、不执行任何传入的命令，然后退出 0** —— 结果就是**静默空转**：无任何输出、退出码 0、被调用的命令从未运行。确需 `env` 时写绝对路径 `/usr/bin/env`。
  - ❌ `"VAR=value" cmd`
- **「退出码 0 + 无输出」不等于成功，可能命令根本没跑**：上面 `env` 那条就是实例（本仓库实测：用它跑一次 E2E 复跑，得到 0 字节日志 + `exit=0`）。凡**结论依赖某条命令真的执行过**的场合（生成证据日志、跑测试、跑门禁），必须**验证副作用**：日志文件非空 / 产物文件存在 / 计数或时间戳变化。**只读退出码会把"没跑"当成"通过"。**
- **控制台编码是 GBK，不是 UTF-8**（Windows 实测两处，表象都是"失败"，实际是编码）：
  - **自己写的脚本输出非 ASCII**（`✓` / `✗` / 中文）会抛 `UnicodeEncodeError` 并**以 exit 1 结束**——看起来像"校验失败"，其实是编码。脚本开头加 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`（范例见 `tools/check-config.py` **文件头的 `reconfigure` 段**；**不写行号**——行号必然漂移，见 §7 尾注与 13.4）。
  - **读本机进程产生的日志是 GBK**：以 UTF-8 检索会 **0 命中**（表象是"日志里没有这条"）；先 `iconv -f GBK -t UTF-8 <log>` 转码再读。
  - **断言与关键词检索一律只用 ASCII 标记**（如 `OptionsValidationException`），别拿中文或符号当判据。
- **临时验证目录不要尝试删除**：`rm -rf` 属本配置的 deny 规则，删不掉（也不要绕）。改用**唯一前缀目录**做镜像验证（**前缀闭集：`.tmp-` / `_tmp-`**——护栏按该前缀把目录排除在「行号引用」等静态扫描面之外；**新增前缀须同时改本句与护栏 `_TMP_PREFIXES`，单边改即 FAIL**），并在产物中**登记其绝对路径**充当取证来源；验证完不清理。
- **长驻进程会锁死构建输出目录，必须约定处置方式**：本地开发服务器（如 `dotnet run` 起的实例）持有 `bin/` 下的 DLL，此后向常规输出目录构建会报 `MSB3027` / `MSB3021`（"文件被 `<进程名> (<PID>)` 锁定"），且**产物停留在改动前的版本**。本仓库实测：该锁使 E2E 复跑的前置条件（"以新 DLL 重启实例"）**跨多轮始终无法满足，整条验证链被堵死**。约定：① 需要构建时一律写临时输出目录（`-p:OutputPath=<临时目录>` / `--output <临时目录>`），不触碰 `bin/`；② **同时必须登记「当前 `bin/` 内产物是改动前版本」这一事实**，并声明哪些验证因此不可信；③ 需要刷新 `bin/` 时明确停服窗口，由主对话调度（你不要自行杀进程）。

## 7. 证据卫生（所有产物适用）

产物的价值取决于**它引用的东西能不能被核验**。本仓库实测：两份已签署产物合计出现 **≥6 处引用不可核验**（详见各产物头部的「证据引用勘误」记录），且每一处都是靠事后人工 + 磁盘核验才发现。五条硬性要求：

1. **证据必须落在测试框架的清理范围之外**：Playwright 默认在**每次运行开始时清空 `outputDir`**（本仓库为 `tests/e2e/.artifacts/`），上一轮的失败截图 / trace 会被后续任意一次运行抹掉，且**不是人工删除**。凡有"运行前自动清理"语义的框架（Playwright / Jest / pytest / `dotnet test` 报告目录）都适用——可持久证据一律写到清理范围之外的路径（本仓库为 `tests/e2e/logs/*.log`）。**程序性前提（E2E，2026-09-20 新增）**：每轮运行**必须**把 `PLAYWRIGHT_OUTPUT_DIR` 指向**本轮独立的目录**（体例 `tests/e2e/_tmp-<唯一前缀>-<日期>-NN/outputdirNN/`）。把该变量做成可覆盖**只是允许**改指向，**不改变**「运行前清空所选 `outputDir`」的语义 —— 连跑两轮若都不设它，两轮都落默认目录、上一轮产物照样被抹掉。该前提是 `51:OBS-08` / `52:OBS-09`（Playwright 失败产物不可持久核验）闭环的**成立条件**。
2. **证据文件名必须含唯一序号**：时间戳到秒**不足以**保证唯一——实测出现过"三次 fail-fast 的日志因**同秒碰撞**聚合进同一文件，归属不可区分"。命名建议 `<用途>-<时间戳>-<序号>.log`。
3. **引用路径落盘前必须逐个做存在性检查**：实测出现过被引证据文件名在磁盘**不存在**（笔误，且同一错名被 3 处引用）、引用的行号与简报不符。**凡在产物中书写的文件路径，写完必须逐个核验存在**。
4. **时间戳由脚本生成、不手填**：元信息块的时间一律取 `date` 的实际输出，**禁止标称钟点**，并保证「冻结时间 ≤ 落盘时间」。**取值与证据口径以 `docs/artifacts.md` §4「冻结时间的判据」为唯一出处**（含日粒度写法、落盘证据只认 git 提交时刻、同一日内不主张先后、冻结后落盘只登记不擅自升版）——本条只写义务，不重述判据。
5. **证据强度必须分级标注**：区分「**版本控制级**」（可用 `git diff` / `git show` 证明）与「**旁证**」（mtime 扫描、锚点互证、sha1 采样、镜像复现）。旁证结论必须在产物中**显式标注为旁证**，不得含混表述（取证优先级见 §1）。同理，在临时镜像目录做的负向验证，须声明「镜像依赖本机缓存 / 源，非生产 CI 环境」并按其证据量级使用。
6. **引用护栏结论必须带校验基线（护栏 T30 机检）**：`python3 tools/check-config.py` 的输出携带一行 `校验基线：HEAD <hash> / 工作区 <干净|脏 N 个文件>`。**任何复述「N 项断言全 PASS」的产物、摘要或结论，必须同时给出该基线**——工作区（有未提交改动）状态下的 PASS 只证明**工作区**，不构成仓库级证明。本仓实测：断言全绿时，护栏自身与它守护的多份文档**全部还没入 git**，而「校验已通过」被当成了「仓库已就绪」。同理，产物引用某个 PASS 时，读者要能回答"那是哪个 revision 的 PASS"。

> 产物间引用一律给**稳定 ID + 文件名 + 原文片段**（规范见 `docs/development-spec.md` 13.4），**禁止只用行号**——行号必然漂移。

## 8. 环境占用与破坏性操作

多角色共用同一台机、同一批容器。**任何人都不独占环境，但任何人都可能污染环境**——本节把"靠临时声明兜着"的做法固化为规则。本仓库实测：执行侧必须反复声明「未触碰主对话实例 `:5180` / `:5198` 与开发库 `luckydraw_dev`」；共享日志被后续批次追加后，报告必须显式声明「该段非本批流量」；破坏性注入批（停 Redis / 持锁）必须自建复位清单。

1. **实例与端口：谁用谁登记，需要就另起**
   - 起实例前先登记「**端口 / 用途 / 归属**」（写入返回摘要首行与产物），避免两个角色抢同一端口而不自知。
   - **不得重启、停用、改配他人实例**（含主对话的开发实例与诊断实例）。需要各自的环境时**另起一个新端口的实例**，而不是"借来用一下"。
   - 手工起实例一律走唯一入口 `tests/e2e/lib/launch-api.mjs`（§5），不要手敲 `dotnet <路径>.dll`。
2. **库与 Redis 分界**：执行侧一律使用**测试库**与**独立 Redis db index**（本仓库：库 `luckydraw_test`、Redis db 2）；**禁止触碰开发库**（本仓库 `luckydraw_dev`）。夹具改动只允许**经环境变量注入或直连测试库**，**不得改** `appsettings*.json` / `launchSettings.json` / `src/`（改运行配置属"必须确认的场景"，需授权）。
3. **破坏性操作三段式**（停依赖、持锁、清库、注入故障、造脏数据）——缺一段都不算完成：
   - **① 事前公示**：操作前把「对象 / 手法 / 时间窗 / 影响面」写入产物，并在返回摘要首行标注（让主对话能在你动手前叫停）。
   - **② 事后复位清单**：逐项复位并**实测确认**，记录复位后的实际值（范式见 `docs/52-qa-report.md` §1.6.6（三）：夹具回默认值 / `FLUSHDB` / 持锁连接数 0 / 容器 Up 且 `PING`）。
   - **③ 归属声明**：复位后仍可能影响他人的部分（共享日志、共享计数器、共享账号）必须显式声明其时间窗与来源。
4. **共用证据文件的归属**：同一日志文件被多批 / 多角色追加写入时，引用方必须声明**批次边界**（起止时刻 + 来源），并显式标注「**非本批流量**」——§7 第 2 条的"文件名唯一"**不足以**确立归属（实测：某批的日志在其后被另一批注入流量追加，含 1 次 500 与多次依赖故障告警，若不声明就会把别人的流量算进自己的结论）。
5. **发现环境被污染时上报、不代他人复位**：不擅自重启服务 / 清库 / 杀进程——那可能抹掉他人正在使用的取证现场。把现象与时刻报给主对话。
