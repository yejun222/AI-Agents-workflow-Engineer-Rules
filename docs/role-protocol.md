# 角色公共协议（所有角色必须先读）

本文件 + `docs/artifacts.md` 与各角色文件共同构成行为约定。**角色文件的「输入要求」应声明先读本文件；冲突时角色文件本身说了算**（它就是该子代理的系统提示）。公共章节只在此定义一份，各角色文件不再重复。

## 1. 总则

- **产物交接的唯一通道是 `docs/artifacts.md` 登记的文件路径**。子代理不继承主对话历史，产物内容靠文件传递，不靠返回摘要（摘要有损压缩）。返回摘要只报告位置与要点，不重复产物全文。
- **写盘必须核验落盘**：返回摘要称已完成但文件不存在时，视为未完成并如实上报。
- **上游契约只读**：`docs/artifacts.md` 标为只读的文件一律不得修改；只写自己「写入范围」列出的文件。
- **禁止递归委派与互相调用**：本配置的 `tools` 白名单不含 `Agent` / `Task`；不产生子代理、不向其他角色派活。
- **上下文省读**：只读需要的段落。先用 Grep 定位关键词，再定点 Read 相关小节，不整份读契约。
- **版本与冻结**：契约文件（00/10/20/30/50/51/52/60）头部含元信息块（产物 / 版本 / 冻结时间 / 上游依赖）；冻结后变更须生成新版本。上游变更后，下游产物须在头部标注「上游 vX 变更，本产物基于 vY，待复核」（失效标记）。需求变更以 `CR-xx` 编号追加在 `docs/00-brief.md` 末尾，不覆盖原文。
- **不提交代码**：任何角色不得 `git commit` / `git push`，除非主对话在调度指令中明确要求。**主对话会在每个评审门后做 wip 提交**（`wip(step-N): …`，用于产物保护与取证）——你在 `git log` 中看到 wip 提交**属正常，不构成你可以自行提交的先例**。
- **能用 diff 就别用旁证（取证优先级）**：wip 提交意味着每一步的产物都有**版本控制级**凭据。凡需要证明「某文件被改过 / 未被改过」时，**首选** `git diff <基线SHA>..<wip 提交> -- <路径>` 或 `git show`；只有当目标确实不在版本控制下时，才退而使用「改动痕迹检索 + mtime + 锚点互证」这类**旁证**，且**必须在产物中显式标注证据强度为「旁证」而非「版本控制级」**（不得含混表述）。

## 2. 信息不足时的处理（无法提问）

子代理在独立上下文中运行，**无法向用户直接提问**。因此：

1. 信息缺失时不要空转、不要反复重试、不要编造。
2. 基于现有信息产出**完整草案**，在草案末尾附「待确认清单」：

   | 编号 | 缺失信息 | 我采用的默认假设 | 若假设不成立的影响 |
   | --- | --- | --- | --- |

3. 在返回摘要首行写明：「存在 N 项默认假设（Q1…Qn），需主对话确认后再定稿」。
4. 只在「缺失信息会导致产出物在结构上不成立」时才中断，并在摘要中写明「无法继续，缺 X」。其余情况一律产出草案 + 假设清单。

## 3. 返回摘要格式

产物写入约定路径后，返回 ≤ 200 字摘要，固定三段：

1. **产物**：文件路径 + 一句话说明
2. **关键决策**：最多 3 条（做了什么选择、放弃了什么）
3. **待处理**：`待确认清单` / `契约冲突上报` / `无`

不要在摘要里重复产物全文。

## 4. 冲突上报

发现上游契约冲突且无法按判定基准裁决时：在返回摘要中用「**契约冲突上报**」开头单列一段，写清各方各自怎么说（引用稳定 ID）、你的倾向、为什么不自行裁决。不要修改任何一份上游契约文件。

## 5. 启动后端实例的前置条件（E2E / 集成验证必读）

违反以下任一条都会得到**误导性的失败结果**（本仓库实测踩过，表象与真实原因完全不符，排查成本极高）：

1. **必须先进到发布目录再启动**：`dotnet <相对路径>.dll` 会把 **ContentRoot 设为当前工作目录**，导致 `appsettings*.json` 不被加载 → 签名密钥为空 → **所有接口返回 500，且日志文件 0 字节**（表象是"程序没起来"，真实原因是配置没读到）。
   - ✅ `cd <publish 目录> && dotnet <项目名>.dll`
   - ❌ 在仓库根目录 `dotnet tests/e2e/deploy/xxx/项目名.dll`
2. **启动逻辑收敛为唯一模板，不许各脚本各写一份**：`tests/e2e/**` 下只保留**一个**启动 helper，其余脚本一律调用它。逐份复制的启动代码正是第 1 条反复复发的原因——每份都可能漏掉 `cwd`。

   ```js
   // ✅ 唯一模板（Node / Playwright）：cwd 锁死发布目录；stdout/stderr 必须落文件，否则第 1 条故障只剩 0 字节日志
   const child = spawn('dotnet', [PUBLISH_DLL], {
     cwd: PUBLISH_DIR,                              // ← 关键行：工作目录 = 生产产物目录
     env: { ...process.env, ASPNETCORE_URLS: `http://localhost:${port}`, ...env },
     stdio: ['ignore', 'pipe', 'pipe']
   });
   ```

   本仓库既有实现：`tests/e2e/coverage.spec.ts` 的 `launchApi()`（分发到新项目时按本项目路径替换本行）。
3. **必须用「签发令牌」做就绪检查，且判据走依赖配置最深的那条路径**：仅探测端口连通、`GET /health` 或**任何匿名可访问的接口**都**不足以**证明实例可用——配置缺失时进程照样监听端口、照常回状态码。
   - **签发路径按项目定**（注册或登录），必须是**用例实际会走的那条**：本仓库为 `POST /api/v1/auth/register`。只钉死一条示例路径，照抄者就会漏掉自己项目里真正会坏的那条。
   - **为什么 `401` 这类判据永远测不出配置缺失**：请求不带 token 时，认证中间件**根本不会进入签名校验**——签名密钥为空它照样返回 `401`。这不是"另一种可接受的探活方式"，是**伪就绪检查**：故障态与正常态给出**完全相同**的信号。（本仓库实测：原有前置核验判据为 `GET /prizes → 401`，恰好绕过唯一会坏的那条路径，烧掉整整 45 轮。）
   - 未通过此检查就开跑，得到的失败结论**无效**——后续每一条"用例失败"都可能只是环境未就绪的假象。

## 6. Bash 调用约定（Windows / Git Bash）

- **环境变量赋值时不要给变量名加引号**：`"VAR=value" cmd` 中 `"VAR=value"` 被 shell 解析为**命令名**而非赋值，会以 `exit 127: command not found` 失败（表象像"命令不存在"，实际是赋值没生效）。
  - ✅ `env VAR=value cmd`（**推荐**，跨 shell 行为一致）
  - ✅ `VAR=value cmd`（变量名不加引号；值含空格或特殊字符时只给**值**加引号：`VAR="a b" cmd`）
  - ❌ `"VAR=value" cmd`
- **控制台编码是 GBK，不是 UTF-8**（Windows 实测两处，表象都是"失败"，实际是编码）：
  - **自己写的脚本输出非 ASCII**（`✓` / `✗` / 中文）会抛 `UnicodeEncodeError` 并**以 exit 1 结束**——看起来像"校验失败"，其实是编码。脚本开头加 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`（范例见 `tools/check-config.py:12-14`）。
  - **读本机进程产生的日志是 GBK**：以 UTF-8 检索会 **0 命中**（表象是"日志里没有这条"）；先 `iconv -f GBK -t UTF-8 <log>` 转码再读。
  - **断言与关键词检索一律只用 ASCII 标记**（如 `OptionsValidationException`），别拿中文或符号当判据。
- **临时验证目录不要尝试删除**：`rm -rf` 属本配置的 deny 规则，删不掉（也不要绕）。改用**唯一前缀目录**（如 `cfgcheck-<时间戳>`）做镜像验证，并在产物中**登记其绝对路径**充当取证来源；验证完不清理。
